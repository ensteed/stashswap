- *HTML/CSS progress bars exist*
- *AWS uploads can report progress*

** 1. Standard HTML progress bar

Use the native =<progress>= element:

** 2. For S3/AWS uploads: yes, progress is available

If you upload directly from the browser to S3, you typically do one of these:

- *presigned PUT URL*
- *presigned POST*
- AWS SDK multipart upload

In the browser, upload progress usually comes from:

- =XMLHttpRequest.upload.onprogress=
- sometimes SDK progress callbacks
- =fetch()= is /not/ great for upload progress in browsers

So if you want a live progress bar, *use XHR or AWS SDK*, not plain htmx.

** 3. htmx and upload progress

htmx is good for server-driven UI updates, but for a direct-to-S3 upload:

- the browser is talking to AWS
- your server is not streaming the bytes
- htmx won’t magically know upload percentage unless you wire custom JS around it

So the common approach is:

1. User drops file
2. Show thumbnail immediately with JS
3. Ask your backend for a presigned S3 upload URL
4. Upload file to S3 with =XMLHttpRequest=
5. Update progress bar from =xhr.upload.onprogress=
6. On success, notify your backend / update UI / attach image to listing

** 4. Typical flow

*** HTML

#+begin_src html
<div id="uploads"></div>
#+end_src

*** JS

#+begin_src js
async function uploadFile(file) {
  // 1. Ask your backend for a presigned URL
  const res = await fetch('/s3/presign', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      filename: file.name,
      contentType: file.type
    })
  });

  const { uploadUrl, publicUrl } = await res.json();

  // 2. Create UI
  const wrapper = document.createElement('div');
  wrapper.innerHTML = `
    <div class="thumb-card">
      <img class="thumb" />
      <progress max="100" value="0"></progress>
      <button type="button">×</button>
    </div>
  `;
  document.querySelector('#uploads').appendChild(wrapper);

  const img = wrapper.querySelector('.thumb');
  const progress = wrapper.querySelector('progress');

  img.src = URL.createObjectURL(file);

  // 3. Upload to S3 with progress
  const xhr = new XMLHttpRequest();
  xhr.open('PUT', uploadUrl);

  xhr.setRequestHeader('Content-Type', file.type);

  xhr.upload.onprogress = (e) => {
    if (e.lengthComputable) {
      progress.value = (e.loaded / e.total) * 100;
    }
  };

  xhr.onload = async () => {
    if (xhr.status >= 200 && xhr.status < 300) {
      progress.value = 100;

      // 4. Tell your app the upload succeeded
      await fetch('/listing_images', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          imageUrl: publicUrl
        })
      });
    } else {
      console.error('Upload failed');
    }
  };

  xhr.onerror = () => {
    console.error('Upload failed');
  };

  xhr.send(file);
}
#+end_src

*** The problem with direct to S3 is then there can be no image checking/processing on the server - so thats a no go

You still have options. “Direct to S3” does *not* mean “no server-side checking/processing.”

Common pattern:

1. browser uploads to S3
2. browser tells your app “here is uploaded object key”
3. your server marks it as *pending*
4. server-side worker/process:
   - validates type/dimensions/content
   - strips EXIF
   - resizes/re-encodes
   - generates thumbnails
   - virus scans if needed
5. only after that does the image become *attached/published* on the listing

So S3 can just be the /temporary ingress/. Your server still controls what becomes usable.

** Two standard architectures

*** 1. Upload to your server, then server sends to S3
Pros:
- simplest validation model
- easy to reject immediately

Cons:
- your app server handles all bytes
- harder to scale
- slower
- progress is only for browser->your server unless you do extra work

*** 2. Upload direct to S3, then server processes asynchronously
Pros:
- scalable
- browser gets native upload progress
- server still validates/processes before publish

Cons:
- more moving pieces
- invalid files may briefly exist in a quarantine bucket/prefix

This second pattern is extremely common.

*** Can't I use htmx somehow to get the thumb cards?

Yes, absolutely — but htmx won’t upload the file to S3 for you /and/ track that direct-to-S3 progress cleanly. It /can/ be used to fetch/render the thumb cards.

Two good ways:

** 1. Use htmx to fetch the card fragment
When files are dropped, your JS can trigger an htmx request to get server-rendered card HTML, then insert it.

For example, keep a hidden endpoint like =/upload-card= that returns:

#+begin_src html

</div>

Then from JS, you can ask htmx to swap it in.

A simple pattern is to create a placeholder div and use =htmx.ajax()=:

#+begin_src js
async function createCard(file) {
  const uploadId = crypto.randomUUID();

  const target = document.querySelector('#uploads');

  await htmx.ajax('GET', `/upload-card?id=${encodeURIComponent(uploadId)}`, {
    target: target,
    swap: 'beforeend'
  });

  const card = document.getElementById(`upload-${uploadId}`);
  card.querySelector('.thumb').src = URL.createObjectURL(file);
  return { card, uploadId };
}
#+end_src

Then JS handles:
- preview image
- S3 upload
- progress updates
- cancel

So htmx is used purely for *HTML fragment rendering*.

** 2. Use a hidden htmx-enabled element per file
You can also create a tiny element in JS and let htmx process it:

#+begin_src js
function requestCard(uploadId) {
  const div = document.createElement('div');
  div.setAttribute('hx-get', `/upload-card?id=${encodeURIComponent(uploadId)}`);
  div.setAttribute('hx-trigger', 'load');
  div.setAttribute('hx-swap', 'outerHTML');
  document.querySelector('#uploads').appendChild(div);
  htmx.process(div);
}
#+end_src

That works too, but =htmx.ajax()= is usually cleaner.

Use:
- *htmx* for server-rendered card markup
- *plain JS/XHR* for direct S3 upload and progress events

That’s a nice combination.

Because once the file is going straight from browser → S3:
- htmx is not the thing sending that request

1. User drops file

#+begin_src js
async function handleFile(file) {
  const uploadId = crypto.randomUUID();

  await htmx.ajax('GET', `/upload-card?id=${uploadId}`, {
    target: '#uploads',
    swap: 'beforeend'
  });

  const card = document.getElementById(`upload-${uploadId}`);
  card.querySelector('.thumb').src = URL.createObjectURL(file);

  const presignRes = await fetch('/presign', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({
      uploadId,
      filename: file.name,
      contentType: file.type
    })
  });

  const { uploadUrl, s3Key } = await presignRes.json();

  const progress = card.querySelector('progress');
  const xhr = new XMLHttpRequest();
  xhr.open('PUT', uploadUrl);
  xhr.setRequestHeader('Content-Type', file.type);

  xhr.upload.onprogress = (e) => {
    if (e.lengthComputable) {
      progress.value = e.loaded / e.total * 100;
    }
  };

  card.querySelector('.cancel').onclick = () => {
    xhr.abort();
    card.remove();
  };

  xhr.onload = async () => {
    if (xhr.status >= 200 && xhr.status < 300) {
      await htmx.ajax('POST', '/upload-complete', {
        values: { uploadId, s3Key },
        target: `#upload-${uploadId}`,
        swap: 'outerHTML'
      });
    }
  };

  xhr.send(file);
}
#+end_src

That’s a very reasonable architecture.

*** I attach the files to a hidden input element. If I was to submit the form, would that send the actual file data to the server for those files?

Yes.

If an =<input type="file">= is inside the form, and the form is submitted as =multipart/form-data=, the browser sends the actual file bytes to your server.

Example:

#+begin_src html
<form method="POST" enctype="multipart/form-data">
  <input type="file" name="photos" multiple hidden>
</form>
#+end_src

Submitting that form sends:

- normal form fields
- file metadata
- actual file contents

A few important caveats:

- The input must be a real =type="file"= input.
- The form must use =enctype="multipart/form-data"=.
- If you submit with htmx, use =hx-encoding="multipart/form-data"=.

Example with htmx:

#+begin_src html
<form hx-post="/upload" hx-encoding="multipart/form-data">
  <input type="file" name="photos" multiple hidden>
</form>
#+end_src

But if your plan is:

- user picks files
- JS uploads them directly to S3
- later submit the form

then the final form submission does *not* automatically resend those uploaded S3 objects just because they were once selected in the file input. It only sends whatever files are currently in the file input at submit time.

So there are two distinct models:

1. *Upload via form submission*
   - file input contains files
   - submitting form sends bytes to your server

2. *Upload directly to S3 first*
   - JS sends bytes to S3
   - form later submits only references, like S3 keys / upload IDs / attachment IDs

In the S3-direct model, after upload you usually store hidden fields like:

#+begin_src html
<input type="hidden" name="uploaded_images[]" value="tmp/abc123.jpg">
#+end_src

Then your server uses those keys to verify/process/attach.

So: *yes*, submitting the form will send the file data if the file input still contains those files and the form is multipart.

The advantage is mainly: *your app server doesn’t have to receive the original upload from the browser*.

That can still be a big win even if your backend later processes the file.

** What direct-to-S3 saves you

Without direct upload:

- browser → your app server
- app server → S3

So your app server handles the full incoming file upload traffic.

With direct upload:

- browser → S3
- then your processing system reads from S3

So your app server avoids being the upload pipe.

That means:

- less bandwidth through app servers
- less memory / request time pressure
- fewer slow multipart requests tying up web workers
- easier horizontal scaling
- better upload progress UX from browser to S3

** But your objection is valid

If your server must later:

- download the file
- inspect/process it
- upload processed result
- delete bad originals

then yes, *you have not eliminated backend file handling*. You’ve only changed /where ingestion happens/.

So the real question is:

> Do I want my web app to be the ingestion path, or do I want object storage to be the ingestion path?

That’s the tradeoff.

** The actual advantage in practice

The advantage is usually not “the server never touches the file.”

It’s more like:

- web tier does not handle upload streaming
- storage becomes the handoff point
- processing can happen asynchronously in workers
- retries/reprocessing are easier
- large uploads are much safer

This matters more when:

- files are large
- uploads are frequent
- many users upload at once
- you have separate worker infrastructure
- processing may happen later / be retried

** For small image uploads, the benefit may be modest

If you are just uploading a few listing photos and each image is reasonably small, then your instinct is right:

- direct-to-S3 may add complexity
- the benefit may be limited
- uploading through your server may be simpler and perfectly fine

That is often the right choice for CRUD-ish apps with moderate image volume.

** One important optimization: don’t route through the web app

Even in a direct-to-S3 setup, the file often isn’t processed by the web app itself.

Instead:

- browser uploads to S3
- S3 event triggers worker/Lambda/job
- worker reads from S3, processes, writes final assets
- app just records status

That avoids tying image processing to your main request/response cycle.

So you’re not doing:

- browser → S3
- browser tells app
- app downloads synchronously inside web request
- app reuploads synchronously

You’re usually doing:

- browser → S3
- storage event / queue
- background processor handles it

That’s the architecture where direct upload shines.

** The hidden benefit: reliability and workflow

S3 as ingress gives you:

- durable temporary storage
- ability to retry processing later
- queue-based workflows
- less risk from interrupted app requests
- easier audit/debug of original uploads

Your app server doesn’t need to “hold onto” the upload while deciding what to do.

** So when is direct upload worth it?

Good fit if:

- uploads are large
- many concurrent uploads
- you want async processing
- workers/Lambda already exist
- web servers should stay stateless/light
- you may later add video or bigger media

Less compelling if:

- files are small images only
- upload volume is modest
- you want immediate synchronous validation/attachment
- your app architecture is simple
- you don’t want queues/background jobs

Even on one server, moving processing out of the web request can still help a bit:

- user upload request returns quickly
- retries become easier
- failures are isolated from the request cycle
- you can limit concurrency deliberately

1. *I/O-bound*
   - upload/download
   - DB calls
   - S3 calls

Node handles this well asynchronously.

2. *CPU-bound*
   - resizing
   - decoding/re-encoding
   - thumbnails
   - image analysis

This is where a plain Node request process is a worse place to do the work.

So if by “processing” you mean actual image manipulation, then yes:

- doing it inline in the main Node process is not ideal
- doing it in a separate process can absolutely help, even on the same server

Because then you get:

- isolation from the web server process
- independent concurrency limits
- crash containment
- better responsiveness for HTTP traffic
- ability to use all cores more intentionally

A single Node process is not great for CPU-heavy work.
A separate worker process using a queue is much better, even on the same machine.

*** So can I, in node, spin up a thread to do some processing and await its finished result?

Yes.

In Node, for CPU-heavy work, the usual tool is *worker threads*. You can send a job to a worker, then =await= the result.

For image processing this is often a good fit.

** Basic idea

Main thread:

#+begin_src js
const { Worker } = require('node:worker_threads');

function runWorker(workerData) {
  return new Promise((resolve, reject) => {
    const worker = new Worker('./image-worker.js', { workerData });

    worker.on('message', resolve);
    worker.on('error', reject);
    worker.on('exit', (code) => {
      if (code !== 0) reject(new Error(`Worker stopped with exit code ${code}`));
    });
  });
}

async function processImage(path) {
  const result = await runWorker({ path });
  return result;
}
#+end_src

Worker file:

#+begin_src js
const { parentPort, workerData } = require('node:worker_threads');
// const sharp = require('sharp');

async function main() {
  const { path } = workerData;

  // do CPU-heavy image work here
  // example with sharp:
  // await sharp(path).resize(300).toFile(path + '.thumb.jpg');

  parentPort.postMessage({ ok: true, path });
}

main().catch(err => {
  throw err;
});
#+end_src

** So yes, you can do

#+begin_src js
const result = await processImage('/tmp/foo.jpg');
#+end_src

and your main request handler can wait for it.

** But a few important caveats

*** 1. Don’t spawn a new worker for every tiny thing forever
You /can/, but under load it gets expensive.

Better options:

- a small worker pool
- a queue with limited concurrency

Libraries like *Piscina* are commonly used for this.

*** 2. Awaiting still means the request is waiting
Using a worker thread prevents the CPU work from blocking the main event loop, which is good.

But if your HTTP handler does:

#+begin_src js
const result = await processImage(...)
res.send(...)
#+end_src

the request is still open until processing finishes.

That may be perfectly fine if processing is quick.

*** 3. Some image libraries already use native threads internally
If you use =sharp=, a lot of the heavy work is done in native code/libvips, and it may already behave much better than pure JS CPU work.

So before building elaborate worker-thread architecture, check whether plain =sharp= in-request is already fast enough for your needs.

*** 4. If processing is slow, a background job may still be better
If it takes noticeable time, it’s often nicer to:

- upload file
- return “processing”
- process in worker
- update UI later

instead of making the upload request wait.

** Practical answer for your use case

Yes, in Node you can:

- upload image to server
- save temp file
- hand processing to a worker thread
- =await= the worker result
- then attach/store final image

That is a reasonable pattern.

** My recommendation
For listing photos, I’d consider this order:

1. try =sharp= directly in the request
2. if that causes responsiveness issues, move processing to worker threads
3. if volume grows, move to a separate worker/queue architecture

#+begin_src js
app.post('/upload', upload.single('image'), async (req, res, next) => {

    res.json(result);
  } catch (err) {
    next(err);
  }
});
#+end_src
